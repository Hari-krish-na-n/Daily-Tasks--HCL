## 6. How to Inspect Bytecode (Day 1 — JVM Internals)

### Disassemble bytecode with javap:
```bash
# After compiling with mvn clean compile
javap -c target/classes/com/auction/PlatformInfo.class
```
This shows the **JVM instructions** (bytecode) generated by the Java compiler.  
You will see instructions like `invokevirtual`, `ldc`, `getstatic`, etc.

### See every class loaded by the JVM:
```bash
java -verbose:class -cp target/classes com.auction.PlatformInfo
```
This prints every class the JVM loads from the Class Loader, including JDK internal classes.  
You will see hundreds of lines like `[Loaded java.lang.String from ...]`

## 7. Day 1 — Java Platform Concepts

### How Java Code Runs (JVM Execution Flow)

```
YourCode.java
    ↓
javac (Java Compiler)
    ↓
YourCode.class  ← Platform-independent bytecode
    ↓
JVM (Java Virtual Machine)
    ↓
Class Loader  ← Loads .class files into memory
    ↓
Runtime Data Areas  ← JVM memory regions
    ↓
Execution Engine
    ↓
Interpreter / JIT Compiler  ← Convert bytecode to machine code
    ↓
Machine Code  ← CPU executes this
```

---

### Key JVM Concepts (Beginner Explanation)

#### JDK — Java Development Kit
The **complete package** a developer needs to write and run Java programs.  
It includes: `javac` (compiler) + `java` (JVM launcher) + `javap` (bytecode inspector) + JRE + development tools.

#### JRE — Java Runtime Environment
The **subset needed to RUN** Java programs (but not write them).  
It includes: JVM + standard Java libraries (like `java.lang`, `java.util`).

#### JVM — Java Virtual Machine
The **engine that runs** your `.class` bytecode.  
It is "virtual" because it is software that behaves like a computer.  
The JVM is what makes Java "Write Once, Run Anywhere".

#### Class Loader
The JVM component that **reads `.class` files** from disk and loads them into memory.  
It works in three phases: Loading → Linking → Initialization.

---

### Runtime Data Areas (JVM Memory)

| Memory Area         | What it stores                                              |
|---------------------|-------------------------------------------------------------|
| **Heap**            | All **objects** created with `new`. Shared across threads. Managed by Garbage Collector. |
| **Stack**           | Each thread has its own Stack. Stores **method call frames** (local variables, partial results). |
| **Method Area / Metaspace** | Stores **class-level data**: class names, method bytecode, static fields. Called "Metaspace" in Java 8+. |
| **PC Register**     | **Program Counter** — stores the address of the current JVM instruction being executed. One per thread. |
| **Native Method Stack** | Like the Stack, but for **native methods** (code written in C/C++ called from Java via JNI). |

---

### Execution Engine

The Execution Engine reads bytecode and converts it to machine code.

#### Interpreter
- Reads and executes bytecode **one instruction at a time**
- Simple but **slow** for frequently executed code

#### JIT Compiler — Just-In-Time
- Detects "**hot code**" (methods called many times)
- **Compiles hot code to native machine code** and caches it
- Next time the method runs, JVM skips interpretation and uses the fast machine code
- Result: Java programs get **faster over time** as JIT optimises them

#### Garbage Collector (GC)
- Automatically **frees heap memory** occupied by objects no longer referenced
- You do NOT need to manually free memory in Java (unlike C/C++)
- Different GC algorithms: G1 GC (default in Java 9+), ZGC, Shenandoah, etc.

## 8. Day 2 — Java Language Fundamentals

### 8 Primitive Data Types

| Type    | Size    | Range / Notes                      | Auction Example              |
|---------|---------|------------------------------------|------------------------------|
| `byte`  | 1 byte  | -128 to 127                        | `auctionStatus = 1`          |
| `short` | 2 bytes | -32,768 to 32,767                  | `totalAuctions = 1250`       |
| `int`   | 4 bytes | ~-2.1B to 2.1B                     | `auctionId = 100001`         |
| `long`  | 8 bytes | ~-9.2 quintillion to 9.2 quintillion | `totalTransactionValue`    |
| `float` | 4 bytes | ~7 decimal digits precision        | `commissionRate = 2.5f`      |
| `double`| 8 bytes | ~15-16 decimal digits precision    | `startingPrice = 50000.00`   |
| `char`  | 2 bytes | Single Unicode character           | `auctionGrade = 'A'`         |
| `boolean`| 1 bit | true or false only                 | `isApproved = false`         |

### Arrays
- **1-D Array:** `double[] bids = {50000, 52000, 55000};`
- **2-D Array:** `double[][] auctionBids = {{50000, 52000}, {30000, 32000}};`
- Index starts at **0** (zero-based)
- Access with: `bids[0]`, `auctionBids[1][2]`

### Constants
```java
public static final double MINIMUM_BID_INCREMENT = 500.0;
```
Use `final` to prevent the value from being changed.

### Type Casting
- **Widening** (automatic): `int → long`, `int → double` — no data loss
- **Narrowing** (manual): `double → int` — decimal part is DROPPED

### Integer Overflow
- `int` max = 2,147,483,647. Exceeding it causes **wrong (wrapped) values** silently.
- Fix: use `long` for large numbers. Always add `L` suffix: `50_000L`

### Floating-Point Precision
- `0.1 + 0.2` in Java ≠ exactly `0.3` due to binary representation limits.
- Never use `==` to compare `double` values.
- Use `Math.abs(a - b) < epsilon` for comparison.
- For financial calculations, use `java.math.BigDecimal`.
